# Bombastic - Innlating2

## Run in VS Code

1. Open the Innlating2 folder itself using File > Open Folder.
2. Open src/App.java.
3. Click Run above main(), or use Run Java.

This is a plain JavaFX project. Maven and launch scripts are not required.
The local VS Code settings select the installed Liberica JDK 25 Full, which includes JavaFX.
On another computer, select that computer's JavaFX-enabled JDK or configure its JavaFX SDK.
The code requires Java 21 or newer. Use Innlating2 as the working directory so img is found.

## Controls

- Blue: WASD to move, Space to place a bomb.
- Red: arrow keys to move, Enter to place a bomb.
- Restart round starts fresh; Main menu returns to the menus.

## Project folders

- src: Java source files.
- img: backgrounds and sprites.
- bin: compiled classes, generated by the editor.
- .vscode, .classpath and .project: basic editor configuration.

## Reading the code

- App creates the window.
- Controller changes screens and starts/stops each round.
- Arena creates the map, players and walls, and handles movement blocking.
- GameView draws the game and receives specific input/button callbacks.
- GameLoop calculates elapsed seconds, calls update, then render.
- GameController handles bombs, explosions, pickups and the winner.
- CollisionDetection uses two workers to check copied entity bounds. Workers only
  detect overlaps; the game thread waits for the results and applies interactions.
- entities contains the player, timed bombs/explosions, walls and four power-ups.

Bombs have a two-second fuse and their flames last half a second. Stone walls stop
blasts; crates are destroyed and stop that blast direction. Bombs trigger chain
reactions. Each bomb can remove at most one life from each player. Crates have a
35% chance of dropping a power-up. Pickups survive flames. Both players dying in
the same update produces a draw. Classic, Forest and Desert have different layouts.

The collision pool is closed when restarting, returning to the menu or closing the
application. Workers use copied, immutable bounds and separate result lists. Game
objects are only changed on the game thread. Movement blocking stays sequential.
Waiting for workers is simple, but may be slower than sequential checks on a small map.
